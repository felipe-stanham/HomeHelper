# T-0005: Second prd instance on Hetzner + multi-host prd deploy

**Status:** [DONE]
**Branch:** `task-T-0005-hetzner-prd-instance`
**Created:** 2026-08-03

## Context

A Hetzner VPS will host a second **prd** instance of Latarnia for clients. Infra
(Caddy, Postgres, Redis, ufw, SSH) is already provisioned by a separate DevOps
process; this task installs and wires Latarnia on it, and — critically — makes
the prd deploy pipeline fan out to **both** prd hosts from a single push to
`main`, so the two instances can never drift to different versions.

Other relevant facts:
- Only one self-hosted runner is registered: id `2`, name `HERMES`, labels
  `self-hosted, Linux, ARM64` (the Pi). Both workflows use bare
  `runs-on: self-hosted`, which becomes **non-deterministic** the moment a
  second runner exists.
- `origin/main == origin/tst == origin/dev` (0 commits divergence), so promoting
  this task to `main` carries no unrelated platform changes to the Pi's prd.
- GitHub environment `production` has a required-reviewer rule (felipe-stanham),
  so every prd run still waits for manual approval.
- Since ufw allows only 22/80/443, this host's prd **must** serve on `:443`.
  `CaddyConfigManager._site_address()` already returns `{domain}:443` for
  `env == "prd"` — no code change needed.
- No router NAT in front of this host: ACME HTTP-01 on `:80` reaches Caddy
  directly, which is simpler than the Pi's port-forward setup.

## Scope

1. Bootstrap Latarnia on `hetzner-latarnia-1` as a self-contained prd instance
   (manual, one-time — the deploy Action does none of this).
2. Convert prd deployment to a **two-host matrix** driven by push to `main`,
   with pinned runner labels and a manual re-deploy escape hatch.
3. Document the new host and the multi-host flow.

Promotion triggers re-checked: no `dataModel.md` change, no new external
service (same GitHub Actions / Caddy / Postgres / Redis stack), and the only
committed code is two workflow files plus docs. One bounded scope — stays a Task.

## Implementation Plan

### Phase A — Runner topology (do first; the workflow change depends on it)

- [x] **A1. Label the existing Pi runner** — add custom label `homeserver` to
  runner id `2` (`POST /repos/felipe-stanham/Latarnia/actions/runners/2/labels`).
  Additive; existing `self-hosted/Linux/ARM64` labels are kept, so the current
  bare `runs-on: self-hosted` keeps matching until the workflows are updated.

- [x] **A2. Register a runner on Hetzner** — GitHub Actions runner (x64) under
  `/home/felipe/actions-runner`, configured with
  `--labels hetzner-latarnia-1 --name hetzner-latarnia-1 --unattended`, using a
  short-lived registration token from
  `POST /repos/felipe-stanham/Latarnia/actions/runners/registration-token`.
  Install as a systemd service (`sudo ./svc.sh install felipe && sudo ./svc.sh start`)
  so it survives reboot. Verify both runners report `online`.

### Phase B — Host bootstrap on hetzner-latarnia-1 (manual, one-time)

- [x] **B1. OS packages** — `sudo apt install -y python3-venv python3-dev
  build-essential libpq-dev postgresql-17-pgvector`. pgvector is a
  platform-default extension (`DEFAULT_EXTENSIONS` in `db_provisioner.py`), so
  the binary must be present or every per-app DB provisioning logs a WARNING.

- [x] **B2. Deploy tree** — `sudo mkdir -p /opt/latarnia/prd /opt/latarnia/backups/prd`,
  `sudo chown -R felipe:felipe /opt/latarnia`, then
  `git clone -b main https://github.com/felipe-stanham/Latarnia.git /opt/latarnia/prd`.
  Create `data/`, `logs/`, `apps/`, `caddy/` under the env root (all felipe-owned).

- [x] **B3. venv + platform deps** — `python3 -m venv /opt/latarnia/prd/.venv` and
  `/opt/latarnia/prd/.venv/bin/pip install -r requirements.txt`. The Action never
  pip-installs; missing `pyotp`/`PyJWT`/`cryptography`/`qrcode` crashes the
  service and fails the deploy health gate.

- [x] **B4. Postgres admin role** — create role `superuser` (`SUPERUSER LOGIN`)
  with a freshly generated password, mirroring the Pi's convention. SUPERUSER
  (not just CREATEDB/CREATEROLE) is required because `db_provisioner.py` runs
  `CREATE EXTENSION vector`, which is not a trusted extension. Local TCP auth is
  `scram-sha-256` per `pg_hba.conf`, so the password is used over `127.0.0.1`.

- [x] **B5. `config/config.json`** (host-local, gitignored — **create before the
  first Action run**, per the `deploy-needs-host-config-json` memory entry).
  From `config.example.json`, with prd values matching the Pi so the two prd
  instances differ only in the Postgres password:
  `postgres.superuser=superuser` + generated password;
  `database_prefix`/`role_prefix` = `prd_latarnia_`; `redis.db=1`;
  `system.main_port=8080`; app port range `8150–8199`; MCP range `9050–9099`.

- [x] **B6. `secrets.env`** (mode 600) — freshly generated
  `LATARNIA_TOTP_ENC_KEY` (base64 32 bytes) and `LATARNIA_JWT_SECRET`. **Not**
  copied from the Pi: separate instance, separate trust domain, separate clients.

- [x] **B7. Caddy include placeholder** — `touch /opt/latarnia/prd/caddy/latarnia.caddyfile`
  **as felipe, not via sudo** (`caddy-include-owner` memory entry: a root-owned
  include makes config generation fail with `[Errno 13] Permission denied`).

- [x] **B8. System Caddyfile** — back up the stock `/etc/caddy/Caddyfile`, then
  install the Latarnia one (`admin localhost:2019` + a single
  `import /opt/latarnia/prd/caddy/latarnia.caddyfile`; no `tst` import — this host
  runs prd only). Reload Caddy.

- [x] **B9. Platform systemd unit** — `/etc/systemd/system/latarnia-prd.service`,
  mirroring the Pi's unit exactly: `User/Group=felipe`,
  `WorkingDirectory=/opt/latarnia/prd`,
  `ExecStart=/opt/latarnia/prd/.venv/bin/python -m uvicorn latarnia.main:app --host 0.0.0.0 --port 8080 --app-dir src`,
  `Restart=on-failure`, `Environment=ENV=prd`,
  `Environment=XDG_RUNTIME_DIR=/run/user/1000` (required for the system-scope
  platform to reach felipe's user-scope systemd), plus drop-in
  `10-domain.conf` → `Environment=PRD_DOMAIN=latarnia-1.stanham.com`.
  `daemon-reload`, `enable --now`.

- [x] **B10. Linger + clock** — `sudo loginctl enable-linger felipe` (per-app user
  units must survive logout) and confirm `timedatectl` shows NTP synced (TOTP
  fails on >~30 s drift).

- [x] **B11. Standalone verification before any Action runs** — service `active`,
  loopback `/health` = `good`, generated Caddyfile at
  `/opt/latarnia/prd/caddy/latarnia.caddyfile` with site address
  `latarnia-1.stanham.com:443`, Let's Encrypt cert issued via HTTP-01,
  `https://latarnia-1.stanham.com/auth/setup` → 200, `/` → 302 `/auth/login`,
  `latarnia_platform_prd` created with the 5 auth tables + `schema_versions`.

### Phase C — Multi-host prd pipeline (the committed change)

- [x] **C1. `deploy-tst.yml`** — pin `runs-on: [self-hosted, homeserver]`. tst
  exists only on the Pi; without the label a tst deploy could land on Hetzner and
  fail (or worse, half-run).

- [x] **C2. `deploy-prd.yml`** — convert the single job to a matrix over
  `[homeserver, hetzner-latarnia-1]` with `runs-on: [self-hosted, "${{ matrix.host }}"]`
  and **`fail-fast: false`** (one host failing must not cancel a deploy already
  in flight on the other — a cancelled mid-deploy host is worse than a failed
  one). Job name carries the host so the run summary shows both. Steps are
  otherwise unchanged: they already read `main_port` from the host's own
  `config/config.json`, so nothing is host-hardcoded.

- [x] **C3. Deployed-commit echo** — add a final step per host printing
  `git rev-parse HEAD`, so the run log is the drift audit trail.

- [x] **C4. `workflow_dispatch` escape hatch** — add a `host` choice input
  (`both` | `homeserver` | `hetzner-latarnia-1`, default `both`) so a host that
  was offline during a push can be re-deployed to the current `main` without an
  empty commit. Matrix computed inline via `fromJSON` on the input — no extra
  GitHub-hosted job.

## Notes

- **Deliberate deviations from the Pi, still open:**
  - `logging.level` was bootstrapped at **`INFO`** for auditability and set to
    **`WARNING`** (the prd convention) after the first Action-driven deploy
    verified green. Resolved.
  - `config/config.json` is mode **600** (the Pi's is 664). It holds the Postgres
    admin password and only `felipe` needs it — the platform, the runner, and the
    workflow's `main_port` read all run as `felipe`. Intentional hardening; not
    worth back-porting to the Pi mid-task.
- **Hardware constraint widened.** `docs/SYSTEM.md` states "Pi 5 with 8 GB RAM"
  as a cross-project constraint. There are now two prd host profiles, and this
  one has 3.8 GB / 2 vCPU. Platform-only footprint is fine; app density on this
  host is lower than on the Pi. Update the constraint wording rather than
  silently violating it.
- **Arch independence.** ARM64 vs x86_64 is invisible to the platform: each App
  gets its own venv built on the host at `prepare` time. The one real
  consequence is that runner selection must never key off the `ARM64`/`X64`
  default labels — hence the explicit custom labels.
- **Same `ENV=prd`, different hosts.** Both instances use `prd_latarnia_`
  prefixes, `latarnia_platform_prd`, and ports `8150–8199`/`9050–9099`. No
  conflict: every resource is host-local (loopback Postgres, loopback Redis,
  local systemd). Do not introduce a per-host env name — the whole point is that
  both hosts run the *same* code from the *same* branch.
- **Client isolation is per-host, not per-app.** This instance exists to serve
  clients separately from the homeserver instance; anything shared between them
  (secrets, tokens, TOTP enrolments) would defeat that. Hence B6's freshly
  generated keys.
- **What the Action still does not do:** pip install, DB migrations, Caddy/ufw
  setup, or anything to gitignored files. `git reset --hard` preserves
  `config/config.json`, `secrets.env`, `apps/`, `caddy/`, `data/`, `logs/`.
  Re-run B3 by hand whenever `requirements.txt` changes.
