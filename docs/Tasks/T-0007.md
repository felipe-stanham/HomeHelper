# T-0007: Commit `tests/cache/` — tester agent script cache

**Status:** [DONE]
**Branch:** `task-T-0007-commit-tests-cache`
**Created:** 2026-08-04

## Context

`tests/cache/` has been untracked since it was first written (2026-06-12), so it
shows up as noise in every `git status`. It needs a decision: track it or ignore
it.

The directory is created by the `tester` agent. Its cache-first workflow
(`.claude/agents/tester.md`) hashes each declarative test entry from `TESTS.md` /
`P-xxxx.md` / `T-xxxx.md`, writes a derived verification script to
`tests/cache/<test_name>.<ext>` plus the spec hash to
`tests/cache/<test_name>.hash`, and reuses the script on the next run when the
hash still matches. The agent definition already states the intended answer:

> The cache is the project's accumulated test logic and is committed to git.
> […] Ensure it is committed (do not gitignore it).

Current contents (2 files, 8 KB):

| File | Role |
|---|---|
| `regression_suite.sh` | Runs `pytest tests/unit/` with an `ENV=prod` refuse-to-run guard |
| `regression_suite.hash` | SHA-256 of the `TESTS.md` test entry lines the script was derived from |

**Verified reusable across machines and sessions:**

- The script is fully portable — relative paths only (`.venv/bin/python`,
  `PYTHONPATH=src`, `tests/unit/`), no absolute paths, no hostnames, no
  credentials, no generated timestamps.
- The stored hash reproduces exactly from the tracked `TESTS.md`:
  `grep -E '^\s*-\s+\*\*[a-z_]+:\*\*' TESTS.md | shasum -a 256`
  → `6af07be5eda0b5e0c592d361d7bdd8eaf64963b78fe4c76a4b2035f7c40142a5`,
  which is byte-identical to `regression_suite.hash`. The cache is current
  against `TESTS.md`, not stale.
- It carries the platform's environment-safety contract (refuse to run when
  `ENV=prod`), which every host should get rather than re-derive.

So neither of the two "gitignore it" arguments holds: it is not host-specific,
and it is not a throwaway byproduct. Committing it means a fresh clone, a new
worktree, or a CI runner reuses the same verification logic instead of a
regenerated variant, which is the whole point of hashing the spec.

## Decision

**Commit `tests/cache/` in full. Add nothing to `.gitignore`.**

No split (commit-some / ignore-the-rest) is needed: both current files are
reusable, and the cache layout has no local-only component. Fixtures, if any are
added later, go to `tests/cache/fixtures/` and are committed too, per the agent
definition.

`.gitignore` already contains a bare `.cache` entry (from the Python template's
coverage-report block). That pattern is dot-prefixed and does **not** match
`tests/cache/`, which is why the directory was showing as untracked rather than
ignored. No change required there — noted so a future reader doesn't "fix" a
conflict that isn't one.

## Notes

- The cache's value is conditional on the hash staying honest. If a `TESTS.md`
  entry is edited, the `tester` agent regenerates the script and the `.hash` file
  changes with it — so cache churn in a diff is a legitimate signal that the test
  spec moved, not merge noise to be squashed.
- Corollary worth keeping in mind: a committed cache means a stale script can be
  inherited by another machine. The agent's rule covers this — a cached script
  that fails while its hash still matches is reported as a real regression, not
  silently regenerated.
