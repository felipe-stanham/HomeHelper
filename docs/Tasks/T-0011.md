# T-0011: `workflow_dispatch` escape hatch for the TST deploy

**Created:** 2026-08-06 | **Status:** [DONE] | **Branch:** `task-T-0011-tst-workflow-dispatch`

## Problem

`deploy-tst.yml` could only be triggered by `on: push: branches: [tst]`. When a push event
fails to produce a workflow run, there is **no way to deploy to tst at all** — no manual
trigger, no re-run to click (a run has to exist before it can be re-run).

This stopped being hypothetical during the P-0011 / T-0010 promotion on 2026-08-06. Two
consecutive pushes to `tst` (`ed436fc`, then an empty commit `1421c51`) each landed on
`refs/heads/tst` and produced **no workflow run**. Everything checkable was ruled out:

| Checked | Result |
|---|---|
| Push reached GitHub | `git ls-remote` and `GET /repos/.../branches/tst` both showed the new SHA |
| Actions enabled repo-wide | `GET /actions/permissions` → `{"enabled":true,"allowed_actions":"all"}` |
| Workflow state | `Deploy to TST` → `active` |
| Trigger correct on the `tst` ref | `on: push: branches: [tst]`, no `paths` filter |
| Workflow YAML valid on `tst` | Both files parse; only two files in `.github/workflows` |
| Runners | `HERMES` and `hetzner-latarnia-1` both `online`, `busy=false` |
| Anything queued / in progress | Nothing |
| `[skip ci]`-style directive | None in any of the 13 promoted commits |
| Repo state | public, not archived, not a fork, default branch `main` |

Root cause remains unidentified and appears to be on GitHub's side. Regardless of cause,
the missing escape hatch is a real gap: `deploy-prd.yml` has had `workflow_dispatch` since
T-0005 precisely so a host that was offline during a push can be caught up without an empty
commit. `tst` lacking it is an asymmetry, and it is the environment where recovery matters
*more*, since tst is where problems are supposed to be caught before prd.

## Decision

Add a bare `workflow_dispatch:` trigger to `deploy-tst.yml`. No inputs: unlike
`deploy-prd.yml`, the tst job is a single job pinned to the `homeserver` runner label, so
there is no host to choose.

**Assumed limitation — tested and found NOT to hold.** I expected GitHub to expose
`workflow_dispatch` only for workflows present on the **default branch** (`main`), making the
trigger inert until promoted. The empirical check (see "Result" below) disproved that for the
API path: `gh workflow run "Deploy to TST" --ref tst` dispatched and deployed successfully
while the trigger existed only on `tst`. The default-branch rule applies to the
*Run workflow* button in the web UI, not to `POST /actions/workflows/{id}/dispatches`. The
workflow file's comment was corrected to state the tested behaviour rather than the
assumption.

- **test_job_still_pinned_to_homeserver:** `jobs.deploy.runs-on` is still
  `["self-hosted", "homeserver"]`, so a dispatch cannot land the tst deploy on a prd-only
  host (the T-0005 constraint)
- **test_dispatch_availability_recorded:** `gh workflow run "Deploy to TST" --ref tst` is
  attempted and its actual outcome (success, or the specific error) is recorded in this
  file, establishing the default-branch behaviour by observation

## Result of the dispatch-availability check

Run 2026-08-06, with `workflow_dispatch` present on `tst` (commit `9bd007e`) and **not** on
`main`:

```
$ gh workflow run "Deploy to TST" --ref tst
https://github.com/felipe-stanham/Latarnia/actions/runs/31128422423
```

The run was created and completed successfully in 2m47s — `Triggered via workflow_dispatch`,
all seven steps green, `Deploy verified: health=good`. So the trigger is usable from the CLI
immediately, without waiting for promotion to `main`.

This also produced the first successful `tst` deploy of the P-0011 / T-0010 promotion, after
two push events had silently failed to create any run. The escape hatch justified itself
within minutes of existing.

### Side observation — the app-count guard in this workflow is dead

Visible in the same log: `Pre-deploy: health=good, apps=-1` and
`Deploy verified: health=good, apps=`. `PRE_COUNT`/`POST_COUNT` come from `GET /api/apps`,
which has required authentication since P-0008, so the unauthenticated `curl` always fails
and both values are empty/`-1`. Consequences:

- The `POST_COUNT -lt PRE_COUNT` regression check can never fire — the deploy is verified on
  `/health` alone.
- The readiness loop's `[ -n "$POST_COUNT" ]` condition is never satisfied, so every deploy
  waits the full 12×5 s before proceeding, which is most of the 2m47s runtime.

Out of scope for T-0011 (which is about the trigger). Filed as a follow-up.
